# OOP Principles Implementation Guide

# 1. Encapsulation

## Rule

Protect internal object data.

All entity fields:

```java
private
```

Expose controlled access only.

---

## Good Example

```java
public class Budget {
    private double remainingBudget;

    public void deductExpense(double amount) {
        if(amount > 0) {
            remainingBudget -= amount;
        }
    }
}
```

---

## Bad Example

```java
public double remainingBudget;
```

---

# 2. Abstraction

## Rule

Hide complex calculations behind simple interfaces.

Frontend should never know:

* formulas
* internal algorithms
* system complexity

---

## Good Example

```java
allowancePredictor.predict();
```

Instead of exposing:

* daily spending formulas
* date calculations
* analytics logic

---

# 3. Inheritance

## Rule

Use inheritance ONLY for real IS-A relationships.

---

## Good Example

```txt
Transaction
 ├── StandardExpense
 ├── SubscriptionExpense
 └── SplitBillExpense
```

---

## Bad Example

```txt
Dashboard extends User
```

---

# 4. Composition Over Inheritance

## Rule

Prefer HAS-A relationships.

---

## Good Example

```java
class Dashboard {
    private AnalyticsModule analytics;
    private GoalModule goals;
}
```

---

# 5. Polymorphism

## Rule

Use shared contracts with different behaviors.

---

## Good Example

```java
interface NotificationService {
    void send();
}
```

Implementations:

* EmailNotificationService
* PushNotificationService

---

# SOLID Rules Context

# Single Responsibility Principle

Every class should have ONE responsibility only.

---

## Good

```txt
ExpenseService
GoalService
BudgetService
```

---

## Bad

```txt
FinanceManagerEverythingService
```

---

# Open/Closed Principle

The system must allow new features without rewriting old logic.

Future additions:

* new transaction types
* new budgeting modes
* new notifications

should be extendable.

---

# Interface Segregation Principle

Interfaces should remain:

* small
* focused
* specific

---

# Dependency Inversion Principle

Always depend on abstractions.

---

## Good

```java
private NotificationService notificationService;
```

---

## Bad

```java
private EmailNotificationService notificationService;
```
